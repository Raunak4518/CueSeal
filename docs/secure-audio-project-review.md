# Secure Audio Screening with ML Match Verification and Signed Evidence

Project review and recommended specification · 12 November 2026

## Decision

Build and evaluate a **verifiable audio reuse screening prototype** against one controlled recording catalog. Existing platform workflows motivate the technical problem. The prototype locates reused audio in an upload, applies a simulated catalog policy, and produces a report another person can verify offline. The academic contribution is a measured comparison of match decisions and a demonstration of how altered requests or index entries can change a signed result. [YouTube Content ID](https://support.google.com/youtube/answer/2797370) · [Pex Attribution Engine](https://pex.com/products/attribution-engine/)

The existing blueprint already has the right fundamentals in §§2–4 and 7. It distinguishes recording identity from legal ownership, separates recognition from policy, and includes no-match handling, secure uploads, and verifiable records. The largest change belongs in §6. Its MERT tagger predicts genre, mood, or instrumentation, while §14 explicitly keeps that model off the critical path. Those outputs add little to the screening decision. Replace that branch with a trained verifier that assesses whether a retrieved candidate has enough acoustic evidence to accept. Make the benchmark and evidence verifier the main deliverables alongside the application. [Engineering blueprint](<../Agent Prompting Playbook - Chat Export/secure_audio_fingerprinting_blueprint.pdf>)

| Blueprint area | Final recommendation | Reason |
| --- | --- | --- |
| Project positioning | Evaluate audio reuse screening and signed evidence against a controlled, approved catalog. | A controlled catalog makes the matching results reproducible and the scope of each report clear. |
| Recognition | Keep spectrogram landmarks, an inverted index, offset voting, and segment localization. | They give a fast, explainable baseline and an explicit estimate of where the recording appears. |
| AI/ML | Train a small candidate match verifier. Remove genre tagging and semantic search from the required build. | The team can measure whether learning helps the actual screening decision. |
| Rights | Use versioned internal policy for recording use, one review queue, and a recorded override. | Missing authority or a conflict can be handled safely without building a rights marketplace. |
| Cryptography | Sign the approved registration and each decision report. Ship an offline verifier with a separately distributed trust key. | A reviewer can detect altered evidence and check which file and policy the report binds. |
| Information security | Prioritize object authorization, catalog integrity, worker isolation, quotas, and media retention. | These controls address attacks that change results, expose uploads, or deny service. |
| Features to defer | Broad format support, live monitoring, semantic search, royalties, full disputes, C2PA support, and advanced infrastructure. | Spend the available time on difficult examples, independent verification, and repeatable tests. |

## What current work establishes

- **Landmark search remains a useful baseline.** Wang’s published Shazam algorithm combines spectral peak pairs, indexed lookup, and time-offset agreement. Apple currently exposes custom catalogs and reference time offsets through ShazamKit. A catalog with time offsets is an established capability, and a local implementation gives the team control over candidate retrieval, thresholds, and evidence. Treat the 2003 paper as the baseline design. Apple documents the current interface and its matching behavior. [Wang, ISMIR 2003](https://www.princeton.edu/~cuff/ele201/files/Wang03-shazam.pdf) · [Apple ShazamKit](https://developer.apple.com/documentation/ShazamKit?changes=la_11) · [audfprint implementation](https://github.com/dpwe/audfprint)
- **Learned fingerprints are a credible extension with a different cost.** Chang et al. trained a contrastive segment encoder. ISMIR 2025 work by Araz et al. studied degradation and offers code and pretrained weights. PeakNetFP targets heavy time stretching, and Panako provides a classical comparison for time-scale and pitch changes. These are useful references for a failure analysis. Reproducing several retrieval engines would take time from the security and evaluation deliverables. Check code, weight, and audio terms separately if trying a research implementation. [Chang et al., ICASSP 2021](https://arxiv.org/abs/2010.11910) · [Araz et al., ISMIR 2025](https://zenodo.org/record/17706424/files/000046.pdf) · [PeakNetFP](https://arxiv.org/abs/2506.21086) · [Panako](https://joss.theoj.org/papers/10.21105/joss.04554)
- **Exact recording and musical version identification are distinct tasks.** A 2026 preprint evaluates both under manipulation and degradation. A separate preprint studies scaling using additional distractors. Benchmark the catalog size used in the experiment, and treat covers, live re-recordings, and shared excerpts as tests of attribution. [Unified Music Identification for Tracks and Versions](https://arxiv.org/html/2608.19919v1) · [Scalable Evaluation for Audio Identification](https://arxiv.org/abs/2509.18620)
- **Platforms document upload matching and misidentification.** YouTube applies configurable actions and restricts which references are eligible, including production loops. SoundCloud says its system can match uploads to unrelated tracks and documents the dispute process. Pex describes matching and licensing for platforms in its product documentation. These sources document existing workflows. Demand for a standalone tool and technical novelty relative to those systems remain unverified. [YouTube Content ID](https://support.google.com/youtube/answer/2797370) · [YouTube reference eligibility](https://support.google.com/youtube/answer/2605065) · [SoundCloud copyright policies](https://help.soundcloud.com/hc/en-us/articles/4402636813979-What-are-SoundCloud-s-copyright-policies) · [Pex Attribution Engine](https://pex.com/products/attribution-engine/)
- **The prototype has two measured results.** On the held-out Song Describer test, the trained verifier accepted the correct recording on 141 of 144 known clips, with zero false accepts on 300 unrelated clips. In a controlled database test, editing the queued intended use and substituting an approved recording's fingerprint postings could change signed results before the integrity fixes. The current worker rejects the edited request and uses verified postings for screening. These results apply to the tested catalog, clips, and attack setup. ## Final workflow and system boundaries

1. A contributor submits a reference recording, source information, and a declared basis for use. A different reviewer approves it for the demo catalog. Bind the approved reference digest to an immutable registration version. Flag duplicate and conflicting claims before activation. Deactivation or supersession changes the eligible catalog without rewriting the historical record.
2. An authenticated uploader submits WAV or MP3. Add MP4 with a single supported audio stream once the audio workflow passes. Hash the original upload, then decode in a restricted worker. Search only the caller’s active catalog. Establish byte, decoded-sample, wall-clock, and duration limits up front. A 60-second query cap is a sensible starting choice for localization and repeatable testing.
3. The landmark retriever emits top candidates, consistent offsets, and the query timestamps that support them. Score each candidate with the verifier. Require sufficient aligned duration and consistent evidence before acceptance. Merge neighboring supported windows only when their alignment agrees. Keep disjoint intervals separate and show competing candidates when the evidence is ambiguous. A time offset by itself supplies alignment, while a segment boundary needs support over time.
4. Store separate recognition and policy statuses. Recognition yields `match`, `ambiguous`, or `no reliable match in this catalog`. Decode and worker errors produce a separate job-failure state. For a match, evaluate the active internal policy for the declared use and date. Use `permitted by catalog policy`, `restricted by catalog policy`, or `review required`. Missing, expired or conflicting authority and ambiguous evidence go to review. A no-match result leaves policy unevaluated. A reviewer can record an override and reason as a new event. Surface segment-level outcomes when an upload contains multiple matches.
5. Export a signed decision report with the match evidence, exact file digest, and policy version. The report states which recording the system matched, where, and which policy snapshot it used. The signature attests to the platform’s record of those results. Decisions about rights outside the catalog stay with the reviewer.

Keep Next.js, FastAPI, PostgreSQL and a background worker. The database can handle the modest catalog index and durable jobs. Use separate identities for the API, worker, and signing operation where practical. A decoder subprocess needs access to its input and scratch directory. Give signing keys and private data outside that job a separate trust boundary. Keep the user interface to registration, upload results, and review with report export.

## The ML experiment

**Research question.** At a fixed false-accept rate on uploads, does a supervised verifier improve correct acceptance of in-catalog recordings under noise, compression, or partial overlap?

- Generate candidates with the same retriever for both systems. Build a strong rule-based baseline using distinct aligned hashes, normalized support, a runner-up margin, and minimum aligned duration. Tune its decision thresholds on validation data.
- Train regularized logistic regression on candidate features. Start with distinct aligned hash count and fraction, dominant offset concentration, support spread across time windows, duration of support, common-hash frequency, and the gap to the next candidate. Mine hard negatives from the retriever’s own wrong candidates. Labels come from the known source recording and supported interval. Keep filenames, titles, track IDs, and artist IDs out of features. Add a shallow tree model only if the linear model leaves a clear, measurable gap.
- Set the operating threshold using query-level outcomes, including out-of-catalog audio, under the same false-accept budget as the baseline. A candidate score is an input to the decision. Label it a probability only if calibration is measured. Keep an ambiguous band and report its review rate alongside accuracy.
- Measure `Recall@K` before the verifier, and compare final outcomes after it. If the correct reference is absent from the candidate list, the verifier has no candidate to recover. If retrieval misses dominate on in-scope transformations, test a research-grade neural fingerprint or a transform-robust retriever as an additional candidate source. Verify actual latency and licensing before adopting it. If the learned verifier fails to improve the precision–recall or review trade-off, publish that result and retain the stronger decision rule. The ML work remains a trained, reproducible experiment.

## Evaluation and acceptance

**Data.** Start with a small development catalog and grow to approximately 100–300 approved references if the corpus supports it. Use team-recorded material for policy demonstrations and per-track licensed audio for broader benchmarking. Record source, creator, license, attribution, digest and redistribution permission for each track. FMA distributes audio under artist-selected terms. Keep benchmark audio permissions separate from simulated platform policies. Ship generation recipes, manifests and fixtures that the team can distribute. [FMA dataset and license terms](https://github.com/mdeff/fma#license)

**Splits.** Split by source recording before generating clips. Group duplicates, alternate encodes, and related recordings or shared-loop families where feasible. Fit on train tracks, choose the operating point on validation tracks, and lock the test set. In the test search index, include the original references for held-out positive recordings so they are discoverable at inference, alongside fixed distractors. Exclude those recordings and derived queries from model fitting and threshold tuning. Hold true unknown recordings out of the search index. Generate different crops, noise sources and transform seeds for final tests where possible. Use the same fixed catalog and queries for both systems.

**Query suites.** Use clean 5-, 10-, and 15-second excerpts. Add MP3 re-encoding, gain changes, resampling, background noise, room effects, and clips placed inside speech or unrelated audio with annotated start/end times. Include full negative uploads of other songs, speech, and silence; hard negatives such as live re-recordings, covers, similar intros, and shared loops; and stress slices for deliberate pitch/time changes and repeated or low-information audio. Mark ambiguous material as such when the clip genuinely fits several references. Report long-upload performance separately because searching many windows increases the chance of at least one spurious match.

| Measure | Definition and initial target |
| --- | --- |
| Candidate recall | Fraction of known queries with the correct track in the top K. Report before verification by duration and transform. |
| Correct acceptance | Correct track accepted per known query. Provisional target of at least 95% for clean 10-second clips on the declared catalog. Count both wrong acceptance and abstention explicitly. |
| False acceptance | Fraction of unknown **uploads** with any accepted match. Report wrong-track acceptance on known uploads separately. Use 1% as a provisional lab operating budget and publish counts and uncertainty. |
| Human review | Ambiguous or uncertain uploads sent to review, as a fraction of the relevant set. Show how much review is needed to achieve the reported false-accept rate. |
| Localization | Median and p95 absolute start/end errors on correctly matched insertions, plus segment recall or IoU so missed intervals remain visible. Start with a provisional median error goal of one second for insertions of at least ten seconds. |
| Runtime | Report p50/p95 decode, feature extraction, candidate search, verification, and end-to-end job times. Keep the blueprint’s provisional p95 search goal under two seconds for a ten-second query and state hardware, catalog size and concurrency. Also report index size. |

For a sub-1% claim, zero false accepts in 300 independent negative uploads gives an approximately 1% one-sided 95% upper bound under a binomial model. Repeated crops of the same recording do not supply that many independent trials. Report recording-level uncertainty or grouped bootstrap intervals where feasible, and disclose when the sample is too small. Class prevalence matters: at 1% prevalence, 95% sensitivity and a 1% false-accept rate yield roughly 49% precision under those assumptions. This is a reason to retain review and report operational rates alongside balanced benchmark results. All targets here are proposals, pending measurements.

## Cryptography and threat model

- **Exact file binding.** Compute SHA-256 on original uploaded bytes and approved reference bytes. A re-encoded clip can still match acoustically and will generally have a different byte digest. The report verifier can recompute the digest when the original file is available. [NIST Secure Hash Standard](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)
- **Authentic records.** Sign versioned, canonical JSON with Ed25519 from a maintained library. Include a record type, schema version, tenant and resource IDs, digests, reference and catalog versions, matched intervals, algorithm/model/threshold versions, signed policy ID/version and outcome, report ID, issuer, and key ID. Use a consistent timestamp convention and integer milliseconds for intervals. Ship a small offline verification command and a public key or trusted key set through a separate distribution path. Verify the expected schema and record type, reject untrusted keys, and check the supplied file digest. A valid historical signature can still refer to a superseded policy. For a current decision, check revocation or freshness against trusted current state. A server-supplied timestamp is an issuer assertion. [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.html) · [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html) · [RFC 3161 timestamp protocol](https://www.rfc-editor.org/rfc/rfc3161.html)
- **Private media.** Use TLS for network deployment and restrict media access to its tenant and permitted actor. Delete query audio and scratch outputs after a short documented retention window. Store retained media in authenticated encrypted storage. If implementing AES-GCM directly, use a library, unique nonces per key and separate encryption/signing keys. Test tampered ciphertext, wrong keys, and cleanup after failed jobs. Keep keys out of the DB, source tree, and media worker. [OWASP ASVS](https://asvs.owasp.org/)
- **Audit integrity.** Record reviewer actions, policy changes and exports as append-only events at the application layer. If keeping the blueprint’s hash chain, commit the business action and event transactionally and retain a signed chain head with sequence number outside the database. Test rollback or truncation against that separate head. A chain kept only beside its events offers weaker protection against a database rewrite. Prioritize the offline signed report if time is tight.

| Threat | Control to demonstrate | Test to show |
| --- | --- | --- |
| Cross-organization access | Server-side object authorization for every job, preview, catalog lookup and report. | A user from the second test tenant cannot retrieve an object using its known ID. |
| Decoder abuse and resource exhaustion | Strict format limits, no worker network, low privileges, isolated scratch files, CPU/time/disk limits, bounded fingerprint postings and job quotas. | Corrupt, oversized and high-fan-out inputs fail or are bounded. A subsequent normal job completes. |
| Fraudulent or conflicting registrations | Pending status, separate reviewer, provenance record, duplicate and conflict review, and activation only after approval. | An uploader cannot self-approve or cause a pending claim to appear in screening. |
| Tampered report or substituted upload | Verify the signature against a pinned trust key and check the supplied file’s digest. | Change an interval, policy outcome, key, or file and observe the appropriate failure. Verify a valid historical report after a policy update. |
| Evidence leaks and over-retention | Private storage, limited retention and minimal report fields. Exclude raw media and tokens from logs. | Query media and scratch files expire. Authorized access to a retained report still works. |

Use the security checks as demo acceptance tests. OWASP’s object authorization and upload guidance directly address the first two rows. [OWASP API1](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/) · [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## Build order and final demonstration

1. **Prove the task offline.** Create the recording and split manifests. Build the fingerprint CLI and inspect known, unknown and shared-loop queries. Save candidates, offset support and the initial benchmark before polishing the UI.
2. **Train and compare.** Generate candidate features, train the verifier, calibrate against the baseline, and measure where retrieval, verification or localization fails. Freeze model, thresholds and test splits.
3. **Deliver a secure path.** Connect registration approval, private upload, isolated matching, policy evaluation and signed export. Ship the offline verifier and the tests for a swapped file, tampered report, unauthorized access and malicious input.
4. **Finish the evaluation.** Publish the dataset manifest, reproducible commands, per-condition results, error examples, threat model and policy assumptions. Demonstrate a noisy inserted excerpt, an ambiguous shared loop, an unknown upload, a restricted-policy result, and a modified report that fails offline verification.

The project is ready to present when all three disciplines have demonstrable outputs. ML has a trained model and a controlled benchmark. Cryptography has a decision record and an independent verifier. Information security has attack tests against the actual media workflow. The blueprint describes student hardware and an academic schedule as assumptions. The proposed scope is sized for that setting, while hardware performance, rubric interpretation and dataset yield still need validation during implementation.
