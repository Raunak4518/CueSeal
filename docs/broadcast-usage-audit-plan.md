# Broadcast music usage audit plan

Check a submitted music usage report against the audio it describes. The first deliverable is a list of discrepancies with time intervals and evidence a reviewer can verify. GEMA documents a deployed workflow in which SoundAware matches fingerprints from public broadcasts and forwards music usage reports. The PRS reporting format records music titles, timecodes, and durations. Those sources establish the reporting task. Whether this prototype makes review easier is the question for the pilot. [GEMA workflow](https://www.gema.de/en/music-creators/monitoring/public-broadcast) · [PRS reporting format](https://www.prsformusic.com/-/media/files/prs-for-music/licensing/production-music/ipc-terms-and-conditions.pdf)

## Scope and backend design

1. Start with a CLI that accepts one programme audio excerpt, an approved reference catalog, and a CSV of declared cues. Use an explicit program or excerpt identifier and a clip origin for timestamps. Each row has a cue ID, a catalog recording ID, and start and end times. Use integer milliseconds internally. Require a verified mapping when a supplied title or composition identifier refers to a catalog recording. Route unresolved mappings to review.
2. Reuse the authenticated upload job, isolated decoder, verified catalog, and candidate scorer. A synthetic 60-second mono PCM WAV at 8 kHz decoded to exactly 60 seconds. The current job accepts up to 60 seconds of query audio, 180 seconds per registration, and eight million postings per verified snapshot. Start with a fixed subset of complete reference recordings and unchanged excerpts within those limits. Record which references and annotated cues are outside the indexed subset.
3. Add a broadcast annotation adapter and retain the time window and candidate identities for ambiguous matches. The current offline benchmark represents at most one reference and interval per query, and the current scorer accepts at most one candidate per window. Track overlap and unresolved windows explicitly. Score overlapping tracks as a separate test slice so missed simultaneous cues remain visible.
4. Reconcile declared and detected cues by recording ID and interval overlap, using one-to-one assignment for repeated instances. Report a confirmed cue, timing mismatch, detected but unlisted cue, declared cue without reliable evidence, or a case requiring review. Select the timing tolerance before final evaluation. An absent detection or missing catalog entry leaves the declaration unresolved.
5. Sign an audit report that binds the audio and original CSV hashes, excerpt origin, verified catalog digest, matcher version and thresholds, and the findings. Extend offline verification to check both input files. Provide a CSV for review and the signed JSON as the evidence record. Keep the acoustic comparison independent of the existing intended-use policy.

## BAF access and terms

The [BAF audio dataset](https://zenodo.org/records/6868083) is restricted. I checked the public Zenodo API and it exposes no downloadable dataset files. The [separate open Zenodo record](https://zenodo.org/records/7372162) contains the paper. The dataset publisher lists 2,000 reference tracks covering about 74 hours and 3,425 one-minute broadcast excerpts covering about 57 hours, with time annotations. The [reproducibility kit](https://github.com/guillemcortes/baf-dataset) is publicly accessible.

Sign in to Zenodo and request access on the audio record with your academic affiliation, if applicable, and the purpose of the experiment. The record limits use to noncommercial research, prohibits adaptations and derivative works, and requires attribution to the authors and Epidemic Sound. Plan to use the supplied audio unchanged and keep it out of the repository and public demos. Clarify with the provider whether persistent fingerprints and any annotation-derived examples may be retained or shared under the approved terms. Use aggregate metrics for public reporting. Access and the terms for the planned artifacts remain to be confirmed through that request.

Suggested request text

> I am working on a student research project evaluating audio fingerprinting and review tools for broadcast music usage reports. I plan to compare our matcher with the published BAF baselines on the supplied excerpts and annotations. Could you confirm whether local decoding and resampling for fingerprint extraction, storing the resulting index locally for the study, and publishing aggregate evaluation results are covered by the access terms?

## Evaluation

**Matching comparison.** Use the same fixed, verified reference subset and unchanged test excerpts for our rules, our logistic verifier, PeakFP, and Panako. Pin tool versions and configurations. Keep the existing logistic model as the first run. If tuning is needed, use separate validation groups with no adjacent broadcast excerpts across validation and test, and freeze settings before scoring test data. Use the BAF paper's agreement slice and seconds-based precision, recall, and F1. Also report cue-level recall, timestamp and duration error, false flags per hour, and cold and warm runtime. Break out short, quiet background, overlapping, and no-match examples where the annotations support it. Treat the paper's best F1 of 0.47 as a published result on its own setup, and rerun the baselines on our subset for the comparison. [BAF paper and metrics](https://archives.ismir.net/ismir2022/paper/000109.pdf) · [Baseline configurations](https://github.com/guillemcortes/baf-dataset/tree/main/configs)

**Report checking comparison.** Use project-owned or otherwise permitted fixtures while access is pending. For the broadcast experiment, use approved annotation-derived test reports with reproducible missing rows, wrong recording IDs, wrong times, duplicates, and intact controls. Run manual review, review assisted by the strongest baseline, and review assisted by our matcher. Feed both matchers into the same reconciliation rules and use the same report format so the test isolates the source of any gain. Rotate equivalent clip sets across conditions so a reviewer does not hear the same excerpt twice. Record review time, real discrepancies missed, and false alerts. Injected errors establish whether the checker can find those errors. A workflow trial with real reports and reviewers is needed to estimate operational benefit.

**Acceptance.** First show that the CLI identifies the known discrepancies and that changing either source file or a signed finding fails verification. Treat the system as useful if it cuts review effort at comparable missed-error and false-alert rates, or finds more true errors for the same review effort. If the baseline matcher performs better, retain the reconciler and signed evidence and use the stronger matcher for detection.
